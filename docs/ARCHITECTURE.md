# Архитектура 0.3.4 / SQLite schema 3

## Компоненты

Один Node-процесс, встроенная SQLite WAL, файлы вне public, ES Modules frontend
и MAX Bridge. Нет runtime npm-зависимостей, LLM, ORM и Redis. HTTPS обслуживает
существующий NPM. Webhook с секретом → persistent inbox → транзакция предметной
логики → notifications/outbox → worker с повторными попытками. HTTP использует
HMAC-проверку initData, непрозрачные сеансы, CSRF/Origin, идемпотентность и версии.

## Дерево аренды

```
apartment (физическая квартира, owner_id, общая фотография)
  rental_unit whole / room
    lease (период и условия одной совместной аренды)
      lease_members[] (люди, снимающие этот объект)
      records / comments / events / files / recurring_rules
```

У квартиры есть whole-объект; отдельно можно создать комнаты. Количество комнат
не задаёт число жильцов. В каждой аренде может быть несколько участников. У одного
объекта одновременно одна active/ending аренда. Whole и комнаты не могут быть
активны одновременно: ограничение есть и в domain, и в SQLite triggers.
Планирование нескольких будущих перекрывающихся аренд здесь не реализовано.

`tenant_id` сохранён как legacy-первый участник; авторитетная связь — lease_members.
Нельзя проверять права только через tenant_id. Role — режим интерфейса, не пропуск
к чужим данным. Owner проверяется по apartment.owner_id, арендаторы — по membership
конкретного lease_id. Владелец карточки не проверялся в государственном реестре.

## Видимость и архивы

Собственник видит свои периоды/комнаты. Участники видят shared-записи своей аренды;
расходы/private-документы собственника скрыты вместе с метаданными/событиями/файлами.
Другие комнаты не получают чужих пользователей, комментариев, чеков и документов.
Завершённая аренда остаётся доступной прежним участникам только для чтения.
При новом периоде создаётся новая аренда. Присоединение к существующей группе
открывает общую историю этой же аренды; это не механизм смены жильца с изоляцией
прошлой истории. Индивидуальный выход из группы отдельно от общей аренды не реализован.

## Приглашения

SHA-256 кода, 72 часа, один новый пользователь на ссылку. Повторная выдача не
отзывает другие действующие ссылки. Production join разрешён через подтверждение
в личном диалоге бота. Mini App /api/join — только demo/test. Ссылка переносится
как bot ?start=join_<code>; до подтверждения membership не создаётся. Самоприглашение,
повторное применение и приглашение в завершённый период отклоняются.

## Платежи

Все суммы — целые копейки. `charge.payload.amount` — сумма на всю аренду, не на
каждого жильца. `claims[]`: id, user_id, amount, note, at. `claim` — совместимое
зеркало первой записи. Пока claim не подтверждён, он резервирует часть свободного
остатка, но не увеличивает confirmed. Один незавершённый claim на человека в счёте.
Owner проверяет конкретный claim_id с текущей version. Confirm переносит его в
payments; reject освобождает остаток. Ручная отметка owner может указать payer_id,
который обязательно состоит в этой аренде. Банк не вызывается.

`pending → claimed → partial/paid`; несколько незакрытых claims сохраняют claimed.
Сумма подтверждений не превосходит amount; повторный запрос защищён version +
idempotency key. Компенсация покупки не уменьшает аренду автоматически.

## Счётчики

Прибор/канал хранит kind, label, unit, baseline (целые тысячные), group_id/tariff,
scope, apartment_id, lease_id, active/version. Электричество 1/2/3 тарифа создаёт
1/2/3 канала одной группы. Выбор типа не ограничивает число приборов или подпись.
Схемы тарификации не рассчитывают деньги: сохраняются только показания и расход.

scope=lease — только эта аренда/комната. scope=apartment — общий прибор физической
квартиры, доступный её участвующим группам. UNIQUE(meter_id,period) не позволяет
дважды отправить одно общее значение за месяц. После передачи общих чисел соседняя
комната вводит только свои отсутствующие значения. Новые приборы можно передать
в том же месяце. Общая история ограничена периодом доступа; чужой record_id скрыт,
файлы/комментарии не раскрываются. Начальные значения после записи истории менять
нельзя: при замене архивируют старый прибор. Отключение lease.meters_enabled убирает
ввод и напоминания, не стирая данные. Технический лимит — 100 активных каналов на квартиру.

## Регулярные начисления

recurring_rules + recurring_revisions(from_month). Rule включает amount,due_day,
advance_days,start_month,end_month,state,is_rent,legacy. По умолчанию rent-правило
создаётся с заблаговременностью14 дней; собственник может отказаться в форме аренды.
Рабочие диапазоны: day1–31, advance1–60. 31 февраля становится последним днём февраля.

Worker обходит active/ending аренды с участниками, выбирает условия соответствующего
месяца и создаёт счёт при наступлении окна заблаговременности. Дедупликация:
recurring:<rule_id>:<YYYY-MM>; legacy charge:<lease_id>:<YYYY-MM> также учитывается.
Сумма не зависит от количества жильцов. Повтор worker не создаёт новый счёт.
При восстановлении после остановки пропущенные месяцы с начала активного правила
могут начислиться; pause/resume явно пропускает месяцы паузы.

Правило редактируется только с первого ещё не выставленного месяца или позднее.
Уже существующие счета не переписываются. Пауза/удаление не стирает долговую историю.
Арендный rent/due_day меняется только через terms с согласием всех жильцов. Запланированное
изменение показывается отдельно от current_rent/current_terms; согласованные даты
новых условий идут строго вперёд. При согласованном досрочном завершении отменяются
только нетронутые будущие регулярные счета после даты выезда; оплаченные/заявленные
переводы и ручные начисления требуют отдельного урегулирования.

## Состояния и несколько участников

Ticket: open → in_progress → resolved (ждёт автора-арендатора) → closed. Любой жилец
группы может сообщить, что проблема осталась; confirm — автор заявки (если автор owner,
подтвердить может участник). Только closed показывается в «Решённых».
Purchase: pending → approved → compensated либо rejected. Visit: proposed/counter →
accepted → completed/cancelled. Terms/termination: proposed → accepted/rejected/cancelled.

required_approvals/accepted_by хранят отдельные ответы. Встречное предложение сбрасывает
старые подтверждения. Новому жильцу добавляется обязанность ответа на нерешённые
согласования; уже согласованный будущий визит переоткрывается для его ответа. Выезд:
после согласования owner отдельно завершает аренду при урегулированных записях.

## Уведомления и deep links

HTML-экранирование пользовательского текста; сообщение ограничено длиной, не режет
сущности в середине. Нет доступа к записи — чувствительное содержимое старой очереди
не отправляется. Payload кнопок: r_<record>, c_<record> (обсуждение), l_<lease>, m_<lease>.
Host задаётся MAX_DEEPLINK_BASE. Нельзя использовать Telegram API темы вместо MAX:
оформление следует prefers-color-scheme или явному выбору профиля.

## Эксплуатационные ограничения

Миграции транзакционны, но перед обновлением нужна полная offline-копия БД и файлов.
Откат schema3 на schema2 не реализован. Старый код запускают только со старой копией.
Сеансы живут12ч, файловые ссылки5мин. Снимок state: последние1000 events/200 notifications,
записи/комментарии целиком; перед масштабированием нужны пагинация и нагрузочное
тестирование. Диски и backups не шифруются самим приложением. Подпись файла,
антивирус, государственные/банковские интеграции и юридическая оценка не добавлены.

новой таблицы/миграции нет, схема остаётся 3. Сервис денег, ролей, комнат, MAX-бота
и записей аренды не переписан. `server/version.mjs` читает версию package.json для
health/config и серверного лога, чтобы она соответствовала архиву.
