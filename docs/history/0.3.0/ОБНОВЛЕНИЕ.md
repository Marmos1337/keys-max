# Обновление текущей установки до 0.3.0

Это исходники, не автоматически выполненный deploy. Учтён ваш `current-source.zip`
и контекст: **Nginx Proxy Manager**, `keys-app`, проект `keys-prod`, постоянный том
`keys-prod_data`, HTTPS-домен `keys.udav.team`, публичные юридические страницы,
отдельная цепочка CA. Состояние живого сервера при сборке не читалось.

## 1. Сохраните действующую версию и данные

Не распаковывайте ZIP поверх работающего проекта сразу. Сохраните старый код/образ,
рабочий `.env`, `compose.prod.yml`, `compose.ca.yaml`, сертификаты и конфигурацию NPM
в недоступном посторонним месте. Зафиксируйте используемый image ID и путь установки.
Образы/база нужны вместе для возможного отката.

Все дальнейшие команды выполняются из **нынешнего** каталога приложения на сервере.
Сокращение команды (не меняет конфигурацию):

```sh
dc() { docker compose -p keys-prod -f compose.yaml -f compose.prod.yml -f compose.ca.yaml "$@"; }
dc config --quiet
docker volume inspect keys-prod_data
dc stop app
```

Не используйте `down -v`, `volume prune`, новый project name или новую пустую БД.
Остановка только `app` не выключает NPM и другие приложения сервера.

Для целостной копии старым образом при остановленном приложении:

```sh
dc run --no-deps --name keys-backup-before-030 app node scripts/backup.mjs --stopped --to /app/backups
docker cp keys-backup-before-030:/app/backups ./backups-before-030
```

Перед командой имя временного контейнера должно быть свободно. Проверьте наличие
`keys.sqlite`, `uploads/`, `manifest.json` в выгруженной копии, её контрольные суммы
и доступность копии вне сервера. Только затем удалите служебный контейнер:

```sh
docker rm keys-backup-before-030
```

Не используйте `--rm` перед `docker cp`: копия исчезнет вместе с контейнером.
Флаг `--stopped` — подтверждение администратора, скрипт не останавливает сервер.
Вложения, база, сеансы и `.env` чувствительны; не отправляйте их в публичный Git/чат.

## 2. Замените только код

Распакуйте новую версию в отдельную папку, сравните с установленной и перенесите
исходники. Не заменяйте `.env` файлом-примером и не копируйте демо-данные.
Убедитесь, что версия в `package.json` — 0.3.0.

Сохранены `public/privacy.html`, `public/terms.html`, `public/legal.css` из контекста.
В сервере вместо общего поиска <путь>.html действует явная таблица публичных страниц.
Конфигурация `compose.prod.yml` в поставке — копия предоставленного NPM overlay.
Если после передачи контекста вы ещё меняли его, сохраняйте более свежую конфигурацию.

Проверьте существующие параметры:

```env
APP_MODE=production
PUBLIC_URL=https://keys.udav.team
LOCAL_PORT=3002
MAX_BOT_USERNAME=t414_hakaton_max_bot
MAX_DEEPLINK_BASE=https://max.ru
OPERATOR_NAME=Ключи
SUPPORT_EMAIL=reports@udav.team
PRIVACY_URL=https://keys.udav.team/privacy
TERMS_URL=https://keys.udav.team/terms
```

`MAX_DEEPLINK_BASE` новый, но необязательный: по умолчанию тот же `https://max.ru`.
Рабочие `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`, `SESSION_SECRET` **не меняйте**.
Проверенная цепочка в `certs/max-ca.pem` должна оставаться доступной для read-only
mount; не отключайте TLS-проверку. Порты 80/81/443 оставьте NPM.

## 3. Запуск и миграция

```sh
dc config --quiet
dc up -d --build app
dc logs --tail=100 app
curl --fail --silent http://127.0.0.1:3002/api/health
```

Не публикуйте `docker compose config` без `--quiet`: полный вывод раскрывает секреты.
Должны остаться контейнер `keys-app`, проект `keys-prod`, том `keys-prod_data`.
Миграция 1/2 → 3 выполняется один раз в транзакции до запуска worker.

Что делает миграция: создаёт whole-объект у каждой прежней квартиры, переносит
прежнего арендатора в `lease_members`, сохраняет старое поле `tenant_id` для
совместимости; расширяет счётчики, переносит уже переданные значения; добавляет
правила регулярной аренды и переносит ожидающие подтверждения платежи в claims.
Существующие записи, файлы, comments, events, обложки и сеансы не очищаются.
Мигрированные правила не начисляют заново всю прошлую историю. Старые dedupe-ключи
платежей учитываются: повторного счёта за тот же уже выставленный период нет.

Значительная новая возможность — счёт за следующий месяц может создаться раньше
срока (по умолчанию за 14 дней). После обновления проверьте раздел «Регулярные»:
при необходимости поменяйте заблаговременность или поставьте правило на паузу.
Не удаляйте существующий счёт как способ изменить будущий график.

## 4. Приёмка до открытия доступа

Проверьте `/privacy` и `/terms`: 200 без входа, корректные стили и прежние тексты.
Health не подтверждает доставку MAX. Проверка API бота с теми же CA-настройками:

```sh
dc exec app node scripts/max.mjs check
```

Webhook-адрес и секрет не менялись; повторная регистрация не обязательна, если
подписка уже правильная. Пройдите `ПРОВЕРКА_ДЛЯ_ЗАКАЗЧИКА.md` на разных реальных
аккаунтах: сначала тестовая квартира/комнаты, затем реальные существующие записи.
Не считайте демо-переключение ролей проверкой нескольких настоящих пользователей.

## 5. Откат

При проблеме остановите app, сохраните диагностику и отдельную копию новой базы.
Восстановите **прежний образ/код вместе с полной копией базы и файлов до миграции**.
Нельзя просто вернуть старый код на schema 3 или вручную уменьшить schema_version.
Восстановление в Docker лучше делать на проверенном отдельном томе, затем явно
переключать приложение. Старый том не удалять. Правильность путей и владельца
файлов проверяет администратор; опасного автоудаления томов в поставке нет.

Если после запуска пользователи успели внести изменения, они не находятся в старой
резервной копии. Сохраните их и согласуйте перенос прежде, чем открывать доступ.
