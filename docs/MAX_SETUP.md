# MAX: интеграция версии 0.3.1

В 0.3.1 интеграция сохранена без изменений относительно 0.3.0.

## Уже подключённый проект

В предоставленном контексте указано, что бот `t414_hakaton_max_bot` и мини-приложение
`https://keys.udav.team` уже подключены и работали на 0.2.0. Создавать бота заново,
менять токен и повторять привязку Mini App при обычном обновлении не нужно.
Состояние вашего живого сервера при этой сборке не проверялось. Новые сценарии
0.3.0 нужно принять на реальных аккаунтах после выкладки.

Сохраняйте значения `.env`: MAX_BOT_TOKEN, MAX_BOT_USERNAME, MAX_WEBHOOK_SECRET,
SESSION_SECRET, PUBLIC_URL. MAX_DEEPLINK_BASE добавлен как необязательный HTTPS
origin, по умолчанию https://max.ru. MAX_API_BASE остаётся отдельной настройкой.
Токен бота хранится только на сервере, не во фронтенде или ссылке-приглашении.

## Проверка подключения на существующем NPM-сервере

```sh
docker compose -p keys-prod -f compose.yaml -f compose.prod.yml -f compose.ca.yaml exec app node scripts/max.mjs check
```

Не опускайте CA overlay при сервисных командах: в предоставленной конфигурации он
задаёт NODE_EXTRA_CA_CERTS. Проверенная цепочка монтируется read-only. Не применяйте
NODE_TLS_REJECT_UNAUTHORIZED=0 или curl -k. Цепочка исходящего API и HTTPS сайта
обслуживают разные соединения; сертификат сайта остаётся у NPM.

Рабочий webhook: PUBLIC_URL + `/api/max/webhook`. Секрет сверяется по заголовку
`X-Max-Bot-Api-Secret`; без него сервер ответит401. Событие сохраняется в inbox,
возвращается200, затем worker выполняет предметное действие и формирует outbox.
Повторный callback не создаёт повторный платёж/участника.

Повторная регистрация нужна только если существующая подписка отсутствует или
неверна, а не как обязательный шаг каждого обновления:

```sh
docker compose -p keys-prod -f compose.yaml -f compose.prod.yml -f compose.ca.yaml exec app node scripts/max.mjs register
```

Проверить, что один бот не направляет события одновременно в старую и новую среду.
Не публиковать `.env`, initData, session token или полный config в логах/переписках.
Имя диалога «Хакатон МАХ 414» меняется в настройках MAX, не заменой логотипа в HTML.

## Приглашение: сначала Bot

Собственник выбирает конкретную аренду/комнату → «Пригласить арендатора».
Ссылка: `https://max.ru/<bot>?start=join_<one-time-code>`.
Одна ссылка действует72 часа и добавляет одного человека. Каждому новому жильцу
своя ссылка; выпуск новой ссылки не отзывает старую. Код в ссылке не является
токеном входа в MAX или сеансом приложения — это одноразовое приглашение в аренду.

Открытие ссылки приходит как bot_started с payload. Бот показывает квартиру,
объект аренды и спрашивает подтверждение. Только callback принятия создаёт
membership. После этого кнопка ведёт на конкретный lease. В production нельзя
обойти этот шаг ручным POST /api/join: маршрут разрешён только demo/test.

Проверять на новом аккаунте и уже открывавшем бота. Личный диалог обязателен;
данные аренды намеренно не отправляются в группу. Бот не добавляет пользователя
в чужую аренду по произвольному user_id из клиентской формы.

## Контекстные уведомления

Сообщение содержит заголовок, квартиру/комнату и полезный контекст. Для обсуждения —
имя автора и фрагмент комментария. Пользовательский текст HTML-экранируется,
слишком длинный фрагмент сокращается. Кнопка выбирается по событию, например
«Ответить в Ключах», «Проверить платёж», «Открыть заявку».
Внешний вид стандартных сообщений/кнопок самого MAX не заменяется кастомным UI.

Переходы Mini App через `?startapp=<payload>`:
`r_<record-id>` — запись; `c_<record-id>` — запись и её обсуждение;
`l_<lease-id>` — аренда; `m_<lease-id>` — показания её счётчиков.
На сервере остаётся ACL: наличие ссылки само по себе не открывает чужие данные.
После удаления доступа очередь не должна послать старый чувствительный текст.

## Mini App и безопасность входа

HTML подключает `https://st.max.ru/js/max-web-app.js`. Сервер валидирует подписанную
строку WebApp.initData, HMAC WebAppData, возраст запуска и дубли параметров.
initDataUnsafe не принимается как доказательство личности. Для каждого нового
открытия из MAX проверяются текущие данные запуска, не чужой сохранённый аккаунт.

Ссылка на домен в обычном браузере не имитирует вход MAX. Для локального просмотра
используйте изолированный APP_MODE=demo с вымышленными данными. Не переключайте
реальную установленную базу в demo и не выставляйте demo в публичный production.

Оформление Mini App: системное prefers-color-scheme или выбор в профиле. Никакие
неописанные Telegram themeParams API вместо MAX не предполагаются. Поле темы
сохраняется между сессиями пользователя. Проверить контраст и safe-area на iOS/Android.

## Приёмка и диагностика

Пройти `../ПРОВЕРКА_ДЛЯ_ЗАКАЗЧИКА.md`: несколько аккаунтов, приватность комнат,
комментарий с переходом в обсуждение, отдельное подтверждение каждого перевода,
приглашения, чтение/скачивание PDF, уведомления, встречное время посещения.
Для группового визита бот не предлагает повторно подтверждать тому, кто уже ответил.

401 входа — проверить часы сервера/истёкшее initData и заново открыть приложение.
403 — проверить PUBLIC_URL, Origin, proxy. Нет уведомлений — проверить, начал ли
пользователь личный диалог, профиль events/reminders/bot, subscription, CA и outbox.
health проверяет HTTP/SQLite, но не доставку MAX. После8 неудачных попыток outbox
помечается failed; бесконечного повтора нет. Не выкладывайте чувствительный error/log.
